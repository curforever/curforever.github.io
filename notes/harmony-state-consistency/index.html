Harmony 状态一致性：页面显示 8 点，校验为什么按 9 点？

发表于 2026-10-07 分类于 工程复盘 阅读次数：
本文字数： 1.7k 阅读时长 ≈ 3 分钟
从健康打卡 App 的一个状态不一致问题，整理显示、校验、持久化之间的关系。

在 HarmonyOS 菁英班的小组实践里，我们做过一个健康生活打卡 App。我的面试复盘里记着一个很小、但很典型的问题：目标时间设置为 8 点，页面也显示 8 点，校验却仍然按默认的 9 点处理。

这篇把当时的问题和可以继续完善的方法分开记录。下面的代码是解释状态关系的独立示例，不是原 App 源码，也不是一份可直接运行的完整 ArkUI 工程。

从现象到原因：先问“谁在使用哪份值”

环节 当时观察到的情况 要追问的问题
选择时间 用户修改目标时间 回调更新了哪个变量？
页面展示 显示用户选择的 8 点 展示值从哪里来？
业务校验 仍按默认 9 点判断 校验是否读取了同一个值？

当时通过 HiLog 和页面提醒分析，定位到两条路径：selectedTime 用于显示，currentTime 用于校验。它们没有保持一致。

这里的 currentTime 名称来自当时的记录。在解释模型里，我把两个含义明确写成“目标时间”和“实际打卡时间”，避免变量名进一步造成误解。

页面更新，只说明显示路径收到了变化；并不能证明校验与保存路径也收到了变化。

一个更清楚的状态模型

先把业务状态放到一处，显示和校验都从它派生。示例用“从零点开始的分钟数”表示时间，减少字符串与时间对象混用；跨日、时区及复杂日期仍需要另行建模。

这个示例只解释业务数据。实际 ArkUI 页面还需要使用对应 SDK 版本的状态管理方式，让业务状态变化同步到界面；状态装饰器能够帮助 UI 更新，但不会替开发者消除业务上重复维护的两份值。可结合 HarmonyOS 官方状态管理文档理解数据与 UI 的关系，具体 API 以项目所用 SDK 为准。

保存和重新进入页面，也要走同一条路径

场景 需要验证什么
修改目标时间 展示、校验都使用新值
取消编辑 没有把未确认的草稿写回正式任务
保存后重新进入 持久化值和页面值一致
App 重启 从存储恢复业务状态，再派生显示
首次启动或缺少任务数据 显示可解释的错误，避免把初始化失败统一报成网络错误

我的记录里还有一次“编辑跑步任务时报网络连接错误”的问题，最后定位到初始化数据未入库。当时通过重装触发初始化解决了开发环境问题。进一步完善产品时，应该把初始化或迁移做成可重复执行的流程，并区分数据缺失与网络失败；重装只是一种定位与临时恢复手段。

留给下一次的排查顺序

  1. 重现一条最小操作路径，记录选择、显示、校验三个值。
  2. 对照读写位置，检查是否存在语义相同、分别维护的状态。
  3. 将显示、校验与保存统一到明确的业务状态。
  4. 覆盖取消、重入、重启和首次初始化，验证完整生命周期。

这次小问题让我更重视“状态由谁负责”。以后看到页面已经更新，我还会继续检查：业务规则和存储是不是也在读这一份状态。
