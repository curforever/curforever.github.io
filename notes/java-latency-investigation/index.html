Java 接口慢：先把时间花在哪里说清楚

发表于 2026-10-07 分类于 工程复盘 阅读次数：
本文字数： 1.6k 阅读时长 ≈ 3 分钟
从请求链路、慢查询日志到 SQL 执行计划，记录证据与索引判断的方法。

我在实习与面试复盘中整理过慢查询、索引和 EXPLAIN 相关笔记。回头看，最有用的部分是先收集证据，再决定优化哪一段；一些方便记忆的口诀则需要补上适用条件。

这篇根据这些记录整理排查方法，使用独立构造的学习用 SQL 示例。重点是如何验证判断，以及哪些条件会影响结论。

先拆请求链路，再检查数据库

观察结果 下一步验证 不能直接下的结论
某条 SQL 耗时明显 SQL、参数、执行计划、扫描情况 接口慢一定是索引缺失
SQL 单独快，接口仍慢 连接获取、队列等待、外部调用和循环查询 数据库没问题，所以无需再看调用方式
平均值正常，偶尔很慢 分位数、并发负载、锁等待及关联请求 平均值够低，用户体验就没问题
返回记录很多 必要字段、分页与返回体大小 单纯增加线程就能解决

应用侧耗时记录和 MySQL 慢查询日志能回答不同问题。慢查询日志是诊断线索，具体记录规则还取决于配置；它并不能代表整条请求链路。参见 MySQL 慢查询日志文档。

先查看计划：

计划字段 我要看什么
type 当前访问方式是否与查询规模相称
possible_keys / key 候选索引与实际选择的索引
rows / filtered 估计扫描量与过滤情况，不把估计当成实测
Extra 排序、覆盖索引等补充信息，结合完整查询判断

对于这个查询，(user_id, status, created_at) 可以作为待验证的复合索引候选。是否值得创建，需要结合数据分布、现有索引、其他查询和写入成本，不能只凭这一条 SQL 决定。

复合索引需要结合最左前缀理解，而不是机械套用“关联列 → 条件列 → 返回列”的固定顺序。相关机制参见 MySQL 多列索引文档。

三句容易记住，但容易说过头的话

简化说法 更准确的理解
SELECT * 会让索引失效 它不必然导致索引不可用，但可能增加返回数据和回表开销
出现 OR 或 NOT IN 就不会用索引 需要结合查询、数据分布和优化器选择查看计划
索引越多，查询越快 索引增加存储与写入维护成本，应该服务于实际访问模式

在 MySQL 8.0.18 及后续支持的版本里，EXPLAIN ANALYZE 可以提供实际执行过程的信息，但会真正执行语句。这和只查看估计计划不同，使用前要确认查询成本和环境。参见 EXPLAIN 官方文档。

怎样判断修改有效

要保持一致的条件 要比较的证据
相同数据、参数与并发设置 请求耗时分布、扫描量、执行计划
明确冷缓存或热缓存状态 避免把缓存预热当成索引收益
包含有代表性的参数 避免只测最容易命中的用户或时间范围
关注读取与写入 检查索引修改是否增加其他操作成本

我希望留下的是一套可复用的排查顺序：定位耗时区间、提出假设、收集证据、做最小修改，再在一致条件下验证。最终记录的结论应该能解释“为什么有效”和“在哪些条件下有效”。
